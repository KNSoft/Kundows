# Fixtures for the FAT32 volume flush investigation

The [investigation](../README.md) gives the conclusions. The following fixtures check different boundaries:

- **Volume API:** from an x64 MSVC prompt, use [`Volume/build.cmd`](Volume/build.cmd) for `fatflush.exe` and [`Volume/build-cycle.cmd`](Volume/build-cycle.cmd) for `fatcycle.exe`. Both write to `OutDir/ApiTests/`. [`New-FatFixture.ps1`](Volume/New-FatFixture.ps1) creates a fresh 512 MiB FAT32 disk with a 1 MiB partition offset, 4 KiB clusters and the fixture label. Give each system a separate copy. `fatflush.exe X:` checks both FAT copies **immediately after the flush returns**; [the paired results](../Evidence/FatFlush.tsv) include the reads before and after. `fatcycle.exe X:` separately verifies three lock/dismount/remount cycles, 8 MiB each. Use the disposable fixture volume, not a system drive.
- **ReactOS kernel lifecycle:** [`Lifecycle/build.py`](Lifecycle/build.py) builds the guest-only synthetic-stream driver and controller using the x64 MSVC build inputs. It does not attach to a storage device. The original V1 tool ran eight conditions/39 checks; later versions added the failed-purge and overlap cases. [`summarize.py`](Lifecycle/summarize.py) checks that the controller log is complete before scoring it. See [V1 results](../Evidence/CcCycle.tsv) and [candidate results](../Evidence/CcOwnership.tsv). These are not the Windows observer's case numbers.
- **Windows observer:** start with the [case definitions and execution table](../README.md#windows-lifecycle-cases) before reading the debugger output.
- **Size and close:** [`file-size-contract.c`](file-size-contract.c) uses two ordinary file handles; [`size-ddi.c`](size-ddi.c) calls CC directly and reads the supplied kernel events. To check the saved receipts, run `python Docs/Notes/FAT32-Volume-Flush/Tests/compare-size-runs.py` from the repository root. It compares driver identities, DDI values and complete program output; it does not boot a VM.
