# FAT32 镜像写入：第 311 扇区的提交、完成和读回

**封存盘的 29 个差异全部落在一个 512 字节扇区。** FAT1 的第 39907–39935 项缺失；这是第 311 扇区的最后 29 项（扇区从 0 开始）。`PALAI.TTF` 的目录项要求 68 簇，首簇 39907；从 FAT1 只能走 1 簇，从 FAT2 可走 68 簇。后续测试从三个位置观察同一扇区：fastfat 送交每份 FAT 时的内容、下层 IRP 的完成结果、第一次硬盘启动菜单上的离线读回。

| 样本（Hyper-V，1 vCPU，8 GiB IDE） | 首簇，FAT1/FAT2 链长 | 第 311 扇区 SHA-256，FAT1 / FAT2 |
| --- | --- | --- |
| 原故障盘，已发生故障和重启；只读副本 | 39907，1 / 68 | `95a4a303…18e37d5` / `7fd8ec02…20d7238` |
| 同一原 ISO 再次空盘安装，文本安装结束 | 39907，68 / 68 | 均为 `7fd8ec02…20d7238` |
| 当前修复集加诊断驱动，文本安装结束 | 39908，68 / 68 | 均为 `129476ea…bdd5c96` |

分区起点 1,048,576 字节；卷内保留区 16,384 字节，每份 FAT 8,371,200 字节。在全部样本中两份第 311 扇区的**虚拟磁盘绝对位置**分别为 **1,224,192** 和 **9,595,392**。诊断介质的文件布局让字体首簇后移了一项，但它仍从同一扇区起步。不能要求两种介质的扇区内容逐字节相同。

## 原 ISO：虚拟磁盘层

使用当时的 ISO `9E2A967AE0004DE2785E42D976FA951A26519A220AC30EA020D862BB5BFC3DCB`，不更换来宾文件。用宿主 `Microsoft-Windows-VHDMP` 的 IO 关键字记录，再以目标叶差分盘**完整路径**筛选。从空盘到首次硬盘 FreeLdr 菜单，配对 46,234 个 1001/1002 活动；无缺失的开始/完成，无不一致的偏移/长度，无 1010/1011 恢复错误事件。`tracerpt` 报告整段 ETL 丢失事件数为 0。每份 FAT 与 204 个写请求相交，覆盖字节数（含重复）均为 8,580,608。

两份目标扇区各经历一次 65,536 字节格式化范围写，以及一次 3,072 字节范围写；后者从各自 FAT 的相对偏移 156,672 开始。两者均有结束事件。菜单上保存 VM，从只读挂载的叶盘副本核对，两份 FAT 全表 SHA-256 与原故障盘的第二份 FAT 完全一致：`83eede5987c5afb777c4df69f71a0c9eb4552c5a1250f9f3e23d2838178bdb88`。

**再用同一原 ISO 做一次独立空盘安装，延长追踪至首次图形向导。** 在硬盘菜单和向导欢迎页分别保存磁盘副本。菜单上两表都是 `83eede59…`，欢迎页上两表都变为 `f56d3207…`，两个时间点的表内差异均为 0；目标扇区的哈希两次都是 `7fd8ec02…`，字体在两份表上均为 68 簇。49,381 个宿主活动完整配对，ETL 丢失事件数为 0，每份 FAT 与 598 个写请求相交。此轮目标扇区上的第二次写入是 4,096 字节（相对偏移 155,648），不同于上一轮的 3,072 字节；两次都包含完整的第 311 扇区。硬盘菜单到欢迎页期间没有覆盖第 311 扇区的写请求。

同一次追踪还覆盖了[损坏盘 Debug 入口报告的两个文件](DebugReplay.md)。`PAGEFILE.SYS` 和 `SYSTEM.ALT` 在硬盘菜单上都不存在，到欢迎页时两份 FAT 上都有完整的链。用 `summarize-vhd.py --entry 2031618` / `--entry 397383` 分别查看两者首簇所在的 FAT 第 15872 / 3104 扇区：在菜单之后，每份 FAT 各有一次包含相应扇区的写请求，长度分别为 4096 和 1024 字节。它们与文本安装期间的字体扇区写入分属两个时间段。

## 诊断 ISO：来宾与宿主同一次运行

仅供调查的[探针补丁](fat-mirror-probe.patch)观察 x64 Debug 的 FAT32 双镜像卷文件路径。在 `FatMultipleAsync` 送出两个子 IRP 前记录组号、镜像、VBO/LBO、长度；在 `FatMultiSyncCompletionRoutine` 释放 IRP 前记录确切 NTSTATUS 与 `IoStatus.Information`。顺序号全局递增。覆盖目标扇区时从原始 MDL 取 512 字节快照。表位于非分页内存；不在每次写入时打印、写日志文件或增加锁。关机时卷循环结束、全局锁已释放，再留一个有上限的 90 秒窗口供宿主保存 RAM。

诊断 ISO SHA-256 `41568791527BCF7972473894BFAD751F907E3DFEB9A3365672D0A507E399ABF3`。**74 批、148 次写入、296 个顺序事件完整；全部状态为 0，完成字节数均等于请求长度。** [74 批逐项记录](MirrorRequests.tsv)中 `first_sector` 相对于各自 FAT；`submit` / `done` 是来宾侧的调用和完成次序。

| 批次 58 | 卷内 LBO | 请求 / 实际字节 | 提交 / 完成 | 提交时的目标扇区 SHA-256 |
| --- | ---: | ---: | --- | --- |
| FAT1 | 172032 | 4096 / 4096 | 229 / 231 | `129476eabde5cb874debf3dbfcb08f0f931ea1911910823f1db3ce87fbdd5c96` |
| FAT2 | 8543232 | 4096 / 4096 | 230 / 232 | 同上 |

两次提交先于两次完成。宿主追踪中，148 个来宾写入的绝对偏移和字节数全部能按重复次数对上；两份 FAT 各与 203 个宿主写请求相交。格式化写入等其他路径也会出现在宿主层，因此不把宿主的全部写入都计为这 74 批。宿主配对活动 46,229 个、ETL 丢失 0；宿主 1002 事件本身不含 NTSTATUS，表中的成功状态来自**来宾子 IRP**。在随后的首次硬盘菜单暂停、复制并只读挂载磁盘，两份目标扇区与提交时的 512 字节样本相同，1121 个文件未见短链，51 个字体与 CAB 相同。

## 待核实：一份镜像返回成功但字节数不足

在 x64 MSVC 命令行运行 `python Docs\Notes\HyperV-Desktop-QA\FatTrace\check-short-write.py`。[宿主检查](check-short-write.py)提取固定版 `FatMultiSyncCompletionRoutine` 和 `FatCommonWrite` 等待后的处理分支，模拟每份各请求 4096 字节，交换两次完成的先后顺序。第一份始终成功写满：

| 第二份的模拟完成结果 | 父请求状态 / 字节数 | 从脏区记录移除的字节数 |
| --- | --- | ---: |
| 成功 / 4096 | 成功 / 4096 | 4096 |
| 成功 / 512 | **成功 / 4096** | **4096** |
| `STATUS_IO_DEVICE_ERROR` / 512 | `STATUS_IO_DEVICE_ERROR` / 512 | 0 |

两种次序结果相同。这个对照确认了 fastfat 对**正数短写**的处理；上述 148 个实际子请求都没有出现这种返回。要判断它是否能在本机造成盘面差异，下一步需核对来宾实际存储栈会将短写转成错误，还是会把成功状态和短长度一起交给 fastfat。

## 复核方式

- **磁盘读回。** 在测试 VM 已保存或关机时复制差分盘，核对父盘与容量。以 `Mount-VHD -ReadOnly -NoDriveLetter` 挂载**副本**，确认磁盘只读后，将 FAT32 卷 GUID 传给 [`read-mirrors.py`](read-mirrors.py)。脚本读取两份表和字体目录项，仅在指定输出文件中写入摘要。
- **宿主 ETW。** 在测试机上以独立会话启动 `logman start <name> -ets -p "{e2816346-87f4-4f85-95c3-0c79409aa89d}" 0x2 5 -bs 128 -nb 16 128 -o trace.etl`，测试后 `logman stop <name> -ets`。从 `Get-VMHardDiskDrive` 保留实际叶盘路径、从 `Get-Partition` 保留字节偏移；记录暂停时间（UTC）。用 [`Export-VhdIo.ps1`](Export-VhdIo.ps1) 导出本盘活动，再用 [`summarize-vhd.py`](summarize-vhd.py) 与读回 JSON、分区偏移及可选的来宾 `writes.tsv` 对照。
- **来宾记录。** 只在临时测试树中把探针补丁施加于 `4fbbefd614b` 的 x64 Debug 源码，用同树 `bootcd` 制作独立诊断介质。在关机留证窗口保存 VM，运行 `python read-trace.py <saved.vmrs> <new-output-dir> --provider <SDK-x64-vmsavedstatedumpprovider.dll>`，再继续启动并取只读磁盘副本。[读取器](read-trace.py)只接受能由虚拟地址反向核对的活动表，检查封闭标志、容量、组号、镜像配对、全部顺序号和快照数。探针不在任何 `Configure.cmd` 补丁列表中。

原始 ETL、保存状态及磁盘副本保存在测试产物中。原 ISO / 诊断 ISO 的 ETL SHA-256 分别为 `03492DD1EFF4482D3341AC08D0008F9F0BF42CD6A4A04BA3394DF9DEBC4F2E64`、`01C7DEE595EDA690B81DCDF8188FD355D88A4CF9F8208978630D7B54D17B0CCA`。

**结论边界。** 现有实测给出了从同批提交到最终读回都一致的对照。封存故障盘没有当时的子 IRP 记录，无法倒推出是提交内容、提交顺序还是之后的覆盖造成那 29 项差异。`PIN_IF_BCB` 未命中后仍可能有脏页的 [C2 检查](../Review/Verified.md#保留的调查项)仍然成立；本轮没有证据把它认定为该次 FAT 分歧的原因。
